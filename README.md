# AI-Factory Best Practices

Deployment and validation best practices for an NVIDIA AI Enterprise (NVAIE) GPU cluster on OpenShift, following the design and build sequence of the internal **AI-Factory Best Practices** document ([docs/AI-Factory-Best-Practices.docx](docs/AI-Factory-Best-Practices.docx)): cluster bring-up, node network configuration, GPU node preparation, the NVAIE operator stack (Node Feature Discovery, Maintenance, Network, GPU operators), and NCCL/training validation.

The sections below mirror that document's table of contents, with each one linking to the manifests, scripts, and test artifacts in this repository that implement it.

## 1. Introduction

Three logical network planes per GPU worker node: a frontend/primary CNI plane (OpenShift SDN, node management), an East/West compute (scale-out) RDMA fabric for NCCL collectives across nodes, and an isolated storage/backend fabric. Before installing with the Assisted Installer, gather every node's hostname, MAC address, static IP/subnet/gateway, plus cluster DNS/NTP/VIPs, and convert that table to NMState YAML for a repeatable, unattended install.

After cluster install: label GPU worker nodes into their own role, then inventory each node's RDMA interfaces and PCIe addresses. [Scripts/cluster-utility.sh](Scripts/cluster-utility.sh) and [Scripts/cluster-utility.ps1](Scripts/cluster-utility.ps1) automate that inventory step — discover nodes by name or role, print RDMA device/PCIe/interface tables filtered by adapter family (ConnectX-7, ConnectX-8, BlueField), and generate `NodeNetworkConfigurationPolicy` (NNCP) YAML directly from what they find.

## 2. Node Network Configuration

The NMState Operator reconciles each node's live network state to a declarative desired state. An NNCP declares the desired interfaces/MTU/VLANs for one or more nodes; NNS is the read-only current state NMState reports back per node. The manifests in [nmstate/](nmstate/) are the NNCP (`nncp-*.yaml`) and NNS (`nns-*.yaml`) objects used on this cluster's workers, generated by the cluster-utility script and applied with `oc apply -f`.

## 3. Configure GPU Node Role

GPU worker nodes need the inbox `irdma`/`rpcrdma` kernel modules blacklisted (they conflict with the NVIDIA/Mellanox MOFED driver stack), IOMMU disabled, and huge pages configured — isolated behind a dedicated `MachineConfigPool` so only GPU workers reboot for these changes, never the rest of the cluster. [Misc/custom-role-gpuworker.yaml](Misc/custom-role-gpuworker.yaml) is that `MachineConfigPool`.

## 4. NVAIE Components

NVIDIA AI Enterprise delivers the Kubernetes operators and drivers this cluster depends on:

| Operator | Role | Covered in |
| --- | --- | --- |
| Node Feature Discovery | Labels nodes with detected PCI/GPU/NIC hardware so the operators below can target the right nodes | Installed via OperatorHub; no repo config |
| Nvidia Maintenance Operator | Coordinates cordon/drain for firmware updates and driver reloads | Installed via OperatorHub; no repo config |
| Nvidia Network Operator | Provisions MOFED/DOCA-OFED, RDMA device plugin, and NIC QoS/VLAN configuration | [Section 5](#5-nvidia-network-operator) |
| Nvidia GPU Operator | Provisions the GPU driver, container toolkit, device plugin, and DCGM monitoring | [Section 6](#6-nvidia-gpu-operator) |

A known GPU Operator vs. Network Operator driver-load race is resolved on this cluster by gating the GPU driver on the Network Operator's `network.nvidia.com/operator.mofed.wait` node label — see the `ClusterPolicy`/`NVIDIADriver` split in [Section 6](#6-nvidia-gpu-operator).

## 5. Nvidia Network Operator

`NicClusterPolicy` configures the singleton, cluster-wide components (DOCA telemetry, NIC Configuration Operator); `NicNodePolicy` configures the per-node components (DOCA-OFED driver, RDMA shared device plugin) selected by hostname. `NicConfigurationTemplate` tunes RoCEv2 QoS (PFC/ECN, trust mode) on the backend and storage NICs, and NNCPs (Section 2) set their MTU.

| File | Purpose |
| --- | --- |
| [network-Operator/nicclusterpolicy.yaml](network-Operator/nicclusterpolicy.yaml) | Cluster-wide NIC policy (DOCA telemetry, NIC Configuration Operator) |
| [network-Operator/nicNodePolicy.yaml](network-Operator/nicNodePolicy.yaml) | Per-node OFED driver + RDMA shared device plugin |
| [network-Operator/backend-nic-qos-nic-config-template.yaml](network-Operator/backend-nic-qos-nic-config-template.yaml) | RoCEv2 QoS template for the compute/backend fabric |
| [network-Operator/storage-nic-qos-nic-config-template.yaml](network-Operator/storage-nic-qos-nic-config-template.yaml) | RoCEv2 QoS template for the storage fabric |
| [network-Operator/be-macvlan-network.yaml](network-Operator/be-macvlan-network.yaml) | Backend macvlan `NetworkAttachmentDefinition` |

## 6. Nvidia GPU Operator

`ClusterPolicy` configures every GPU Operator component except the driver (`driver.enabled: false`, `driver.useNvidiaDriverCRD: true`); a separate `NVIDIADriver` object per node supplies the driver itself, gated on the Network Operator's MOFED-ready label so the two operators never reload kernel modules on the same node at once.

| File | Purpose |
| --- | --- |
| [GPU-Operator/gpu-cluster-policy.yaml](GPU-Operator/gpu-cluster-policy.yaml) | Cluster-wide `ClusterPolicy` (toolkit, device plugin, GFD, DCGM) |
| [GPU-Operator/gpu-driver.yaml](GPU-Operator/gpu-driver.yaml) | Per-node `NVIDIADriver` object |

## 7. Testing And Validation

Validated two ways: hand-written Kubeflow `MPIJob`/`TrainJob` manifests (full control over NCCL env vars and privileged pods, used as an independent fabric/driver baseline), and NVIDIA's `nvcrectl` Cluster Readiness Engine (`WorkloadRun`/`Certification` CRDs, NVIDIA's standard report format). Both paths exercise the same NCCL collectives — AllGather, AllReduce, AllToAll, ReduceScatter — plus a short Nemotron5 Megatron-LM training smoke test, and a continuous RDMA QoS/PFC fairness test under sustained load.

| Directory / File | Purpose |
| --- | --- |
| [nccl-training-tests/](nccl-training-tests/) | Hand-written `MPIJob`/`TrainJob` NCCL and training manifests, plus the RDMA QoS pods |
| [nvcre-workloadruns/](nvcre-workloadruns/) | `nvcrectl`-driven `WorkloadRun`/`Certification` manifests and recorded results |
| [Scripts/cluster-utility.sh](Scripts/cluster-utility.sh) | `-T prepare/status/cleanup` sets up the mutating admission webhook `nvcrectl` test pods need for privileged/macvlan access |
| [Misc/nccltestviacmdline](Misc/nccltestviacmdline) | One-off `oc run` NCCL test commands |

See [docs/mpirun-torchrun-test-procedure.md](docs/mpirun-torchrun-test-procedure.md) and [docs/NVCRE-ScaleOut-Certification-MOP.md](docs/NVCRE-ScaleOut-Certification-MOP.md) for the full step-by-step procedures (local to this workspace; excluded from Git — see below).

## Branches And Publication

- `Dev` contains the working collection.
- `main` contains only explicitly selected, reviewed material.
- This is a public repository: **both branches and their commit histories are publicly readable**. Branch protection can restrict changes, not reading.
- Confidential development requires a separate private repository. Never push confidential content to either branch here.

Keep the initial `main` history independent of `Dev`. Publish approved file snapshots in a clean working tree based on `main`; do not merge `Dev` or cherry-pick commits that contain unapproved files. Review the staged diff before every publication. Deleting a file later does not remove it from public Git history.

## Before Using Or Publishing

These files include environment-specific examples, not universally applicable production defaults. Review node names, network interfaces, addresses, storage paths, image versions, and resource requirements before applying them. Follow the relevant procedure and your environment's change-control requirements.

Before pushing to either branch:

1. Review every staged file for credentials, private keys, tokens, customer identifiers, and confidential infrastructure details.
2. Sanitize configuration snapshots, logs, and test results where necessary. Ignore rules are not a security scan.
3. Validate changed manifests and commands in an appropriate test environment.
4. Confirm that documentation links and referenced files exist on the destination branch.

## Contribution Workflow

Develop on `Dev` or short-lived branches based on it. Use reviewed pull requests for changes. Publish to `main` only after the repository owner approves the exact files and their contents.

Configure GitHub rulesets for both branches to require pull requests and prevent force pushes and deletion where supported. Available enforcement depends on the account plan and repository settings; it does not make either branch private.
